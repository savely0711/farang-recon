# Разведка рынка — парсер барахолок Паттайи (Направление 3)

Читает барахолки Паттайи техническим Telegram-аккаунтом и складывает
объявления (ссылка + категория + дата + цена) в Google-таблицу.
Личные данные не собираются. Работает аккуратно: медленное чтение, паузы,
не больше одного нового вступления в группу за запуск.

## Мини-CRM: таблица-воронка (редакция 01.09.2026)

Таблица не список людей, а **воронка продавцов**. Что это значит:

- **Строка = объявление**, а не человек. У продавца столько строк, сколько
  у него объявлений.
- **Повторы отсеиваются по тексту**: тот же автор с тем же текстом (люди каждый
  день поднимают свой пост) в таблицу не попадает и ИИ не тратит — `dedup.py`.
  Второй рубеж — сама таблица: скрипт отбрасывает дубли по ссылке на пост.
- **Колонки**: Ник | Ссылка | Канал | Категория | Дата | Описание |
  Написали? | Присутствие | На сайте. Колонки «Тип продавца» больше нет
  (убрана 01.09.2026): агентствами занимается отдельный контур недвижимости.

**Вкладки (01.09.2026).** Раньше всё лежало на одном листе «CRM». Теперь
объявление попадает на вкладку по статусу его автора, и строка **переезжает
сама**, как только статус меняется — руками, с сайта или ночной сверкой:

| Вкладка | Кто там живёт |
|---|---|
| **Новые** | новые и те, кто не ответил (в «Присутствии» пусто или «нет ответа») |
| **Согласен** | разрешил размещать за него |
| **Отказ** | попросил не трогать |
| **Зарегистрирован** | завёл аккаунт на сайте сам |
| **Без ника** | у поста скрыт автор — писать некому; отсюда строки не ездят |
| **Недвижимость — агентства** | бизнес + категория `realty`; боковой список, строки не ездят |
| **Согласия** | реестр согласий: одна строка на человека |

Переезд делает функция `_resort` в `apps_script.gs`: она читает вкладки воронки
целиком и переписывает их одним `setValues` на лист. Поштучное «вставить строку —
удалить строку» на сотнях строк не укладывается в лимит времени Apps Script.

Кто какой колонкой управляет:

| Колонка | Кто пишет | Значения |
|---|---|---|
| **Написали?** | рассылка «первое касание»; **остановлена 01.09.2026**, колонка осталась как история | Нет / Да / Премиум / Не доставлено |
| **Присутствие** | сайт и Савелий руками; **определяет вкладку** | пусто / нет ответа / согласен / зарегистрирован / отказ |
| **На сайте** | авто-подготовка и ночная сверка | На сайте / Ждёт модератора / Снято; пусто = ещё не пробовали |

**Почему у неудачи нет своего статуса.** Раньше было «Не вышло» (красным).
Савелий 01.09.2026 попросил убрать: глазами статус ничего не даёт, только
пестрит. Теперь ячейка остаётся **пустой, а причина живёт в примечании к ней**
(наведи мышь — увидишь). Это не косметика: пустая ячейка означает «ещё не
пробовали», и без пометки каждый ночной прогон снова тратил бы деньги ИИ на
пост, у которого, например, нет фотографий. Очередь пропускает строки с
примечанием; вернуть их в работу — меню «Фаранг» → «Очистить пометки неудач».

Статусы остаются **на человека**: и «Написали?», и «Присутствие» скрипт
проставляет сразу всем строкам одного ника.

**Меню «Фаранг» в самой таблице** (мышью, без редактора скрипта): пересчитать
«Присутствие» по реестру · разложить строки по вкладкам · перенести старую
вкладку CRM (разово) · удалить архивные вкладки (разово) · очистить пометки
неудач.

## Недвижимость — ОТДЕЛЬНЫЙ контур (с 25.08.2026)

Второй парсер, который живёт рядом и ничего не делит с барахолками:
свой список групп, своя память прочитанного, свой список повторов и **своя
Google-таблица «Фаранг — Недвижимость»**.

**Чего он не делает специально:** никому не пишет (очередь рассылки к нему не
подключена вовсе) и ничего не публикует на сайт. Разделение сделано файлами, а
не договорённостью в коде: `outreach.py` и `prepare.py` читают таблицу
разведки и физически не видят таблицу недвижимости.

**Разбор в два слоя: правила, потом ИИ** (с 25.08.2026). Сначала бесплатные
правила (`realty_extract.py`): сделка, тип жилья, цена + валюта + период,
спальни, площадь, район — район выводится в том числе из названия крупного
проекта («Riviera Wongamat» → Вонгамат), телефоны вырезаются до поиска цены,
залог и коммуналка ценой не становятся. Потом ИИ (`realty_ai.py`) уточняет всё
это и добавляет то, чего правилами не взять: **агентство или частник**,
**название конторы**, жилой комплекс.

ИИ не ответил (кончился баланс Anthropic, сбой сети) — строка всё равно
попадает в таблицу с разбором правилами, прогон не встаёт. Кто сработал, видно
в колонке «Разбор»: «ИИ», «ИИ+правила» или «правила». Выключатель на чёрный
день — `REALTY_AI=0` в `.env`.

**Барахолки тоже пополняют эту таблицу.** Старый `parser.py` каждое объявление
с категорией `realty` копирует сюда вторым экземпляром с полным разбором —
чтобы картина рынка была в одном месте. Это только копия строки: рассылка и
авто-подготовка работают по старой таблице и о новой не знают. Включается само,
когда в `.env` появляется `REALTY_SHEET_WEBHOOK_URL`; недоступна новая таблица —
прогон барахолок идёт как ни в чём не бывало.

**Таблица, две вкладки:**

- «Объявления» — строка = пост: Ник | Ссылка | Группа | Дата | Что это |
  Сделка | Тип жилья | Цена | Валюта | Период | Цена макс | Спальни | Площадь |
  Район | Тип продавца | Агентство | Проект | Разбор | Описание. Дубли по
  ссылке отсекает сам скрипт таблицы.
- «Счётчик» — строка = ник автора: тип продавца, название конторы, за 7 дней,
  за 30 дней, за всё время, первый и последний пост, в каких группах, доля от
  всех объявлений. Тип продавца и контора берутся по большинству постов ника:
  ИИ решает по каждому посту отдельно и иногда ошибается.
  Считаются только предложения — «спрос» (сниму/ищу) в счётчик не идёт.
  Пересчитывается после каждого прогона парсера, ежедневно в 6 утра и кнопкой
  в меню таблицы «Фаранг».

**Файлы контура:**
- `realty_parser.py` — прогон; с сервера запускать через `realtynow.py`
  (`python3 realtynow.py` — добор нового, `python3 realtynow.py 25` — первый
  заход за 25 дней; работает в фоне, лог `realty.log`);
- `realty_channels.py` — список групп (добавлять сюда);
- `realty_extract.py` — разбор текста правилами;
- `realty_sheets.py` — запись в таблицу недвижимости;
- `realty_apps_script.gs` — скрипт-приёмник ТОЙ таблицы (внутри — как ставить);
- `realtysetup.py` — помощник для `.env` на сервере: принимает одной вставкой
  «адрес токен», сам пишет заглавные строки (в консоли Aeza их не набрать) и
  проверяет связь с таблицей (`python3 realtysetup.py`, проверка —
  `python3 realtysetup.py check`);
- `realtycheck.py` — читаются ли группы (в именах помощников нет «_» и
  заглавных: в консоли Aeza они не набираются);
- `realtytry.py` — отчёт о качестве разбора (`python3 realtytry.py 200`,
  с примерами непонятого — `python3 realtytry.py 200 bad`);
- `test_realty.py` / `test_realty_apps_script.js` — самопроверки, гонять после
  любой правки правил или скрипта таблицы.

В `.env` нужны свои две строки: `REALTY_SHEET_WEBHOOK_URL` и
`REALTY_SHEET_TOKEN` (см. `.env.example`). Расписание: 08:30, до обхода
барахолок — чтобы два прогона не читали Telegram одним аккаунтом одновременно.

## Файлы
- `parser.py` — главный скрипт (один запуск = один прогон).
- `login.py` — разовый вход аккаунтом, выдаёт строку сессии.
- `channels.py` — список групп для чтения (на 14.08.2026 — 14 штук).
- `check.py` — проверка: читается ли каждая группа и сколько в ней постов за 7 дней.
  ИИ не тратит, никуда ничего не пишет. Запуск: `python3 check.py`.
- `runnow.py` — ручной прогон разведки в фоне, лог в `recon.log`
  (`tail -n 40 recon.log`). Нужен потому, что VNC-консоль Aeza теряет Shift и набрать
  «nohup … > лог &» руками там нельзя.
- `categories.py` — категории для ИИ (наши 10 + разведочные).
- `classify.py` — ИИ-разбор поста (объявление? категория? цена? частник или бизнес?).
- `dedup.py` — отсев повторных публикаций одного объявления (`dedup.json`).
- `sheets.py` — запись в Google-таблицу (POST в Apps Script Web App).
- `apps_script.gs` — скрипт-приёмник на стороне таблицы (колонки, вкладки,
  дедуп по ссылке, статусы). Правится в редакторе Apps Script; после правки
  обязательно **создать новую версию развёртывания**, иначе изменения не
  вступят в силу.
  **Ручная правка «Присутствия» и «Написали?» (с 20.08.2026).** Оба статуса — про ЧЕЛОВЕКА, а не
  про отдельное объявление. Меняете значение в одной строке — простой триггер `onEdit` разносит
  его по ВСЕМ строкам этого ника. «Присутствие» вдобавок пишется в реестр согласий, перебивая
  прежнее значение (человек сильнее автоматики: можно и снять «отказ»); очистили ячейку —
  очистится у всего ника, запись из реестра удалится. «Написали?» реестр не трогает — это про
  рассылку. Опечатку не разносим. Триггеру новая версия развёртывания НЕ нужна: он работает от
  сохранённого кода.
- `state.py` — память «докуда дочитали» (`state.json`).
- `test_recon.py` — самопроверка питон-части (сеть и Google не нужны):
  `python3 test_recon.py`.
- `test_apps_script.js` — прогон `apps_script.gs` в подставном окружении:
  `node test_apps_script.js`. Гоняй его после любой правки скрипта таблицы —
  дешевле, чем ловить ошибку на живых данных.
- `preparenow.py` — авто-подготовка объявлений в фоне: `python3 preparenow.py 300`
  (лог `prepare.log`). Нужен потому, что прогон идёт долго, а в консоли Aeza
  запущенное не прервать — `Ctrl+C` там печатает букву «c».
- `syncsite.py` — ночная сверка таблицы с сайтом: спрашивает, кто из авторов уже
  зарегистрировался сам (таким ставим «зарегистрирован», и автоматика за них больше
  ничего не публикует), и что стало с размещёнными объявлениями — колонка «На сайте»
  получает одно из значений «В каталоге», «Ждёт модератора», «Снято», «Удалено» (значение
  «Опубликовано» из первых версий упразднено 20.08.2026 — оно значило ровно «Ждёт модератора»;
  встретив его, скрипт таблицы молча переводит).
  Холостой ход: `python3 syncsite.py dry`. «Удалено» и «Не вышло» окончательны —
  чтобы переиграть, очистите ячейку руками.
- `phash.py` — отпечаток картинки (dHash) для поиска дублей на сайте. Считает
  ровно так же, как браузер сайта (`src/lib/phash.ts`): сначала уменьшение до
  144x128, потом честное усреднение блоками 16x16 до сетки 9x8. Второй шаг
  обязателен — без него Pillow и браузер расходятся на 6–8 бит из 64, то есть
  ровно на ту величину, по которой сайт отличает дубль от не-дубля.
- `fillhash.py` — добор отпечатков для уже загруженных на сайт снимков (старые
  фото и всё, что пришло через бота). Спрашивает у сайта список без отпечатка,
  считает и отправляет обратно; новых паролей не нужно. Запуск:
  `python3 fillhash.py` (или `python3 fillhash.py 500` — потолок за прогон).
- `.env` — секреты и настройки (НЕ в git).

## Установка на сервер (Ubuntu, кратко)
```bash
sudo apt update && sudo apt install -y python3-pip git
git clone <репозиторий> recon && cd recon      # или скопировать файлы
pip3 install -r requirements.txt
cp .env.example .env                            # затем заполнить .env
```

### Что нужно заполнить в `.env`
1. `TG_API_ID` / `TG_API_HASH` — один раз на https://my.telegram.org → API development tools.
2. `ANTHROPIC_API_KEY` — ключ ИИ (тот же, что на сайте).
3. `SHEET_WEBHOOK_URL` / `SHEET_TOKEN` — запись в таблицу через Apps Script Web App.
   К таблице привязан скрипт-приёмник (`apps_script.gs`), развёрнутый как Web App;
   URL вида `https://script.google.com/macros/s/.../exec` кладём в `SHEET_WEBHOOK_URL`,
   а общий пароль-токен (та же строка, что вшита в скрипт) — в `SHEET_TOKEN`.
   Пока `SHEET_WEBHOOK_URL` пуст — парсер работает в тестовом режиме (в таблицу не пишет).
4. `TG_SESSION` — получить так:
   ```bash
   python3 login.py      # ввести номер → код из Telegram → пароль (если есть)
   ```
   Скрипт напечатает строку сессии — вставить её в `.env`.

## Ежедневное расписание (cron)
Проще всего поставить всё разом: `python3 setcron.py` (он же `install_cron.py`,
идемпотентно — повторный запуск не задваивает строки). Что получится:
```
0  9 * * *  parser.py    # обход групп: новые объявления в таблицу
0 10 * * *  prepare.py   # авто-подготовка объявлений «согласных» в очередь модерации
40 10 * * * fillhash.py  # добор отпечатков картинок для поиска дублей
20 11 * * * syncsite.py  # сверка таблицы с сайтом (объявления + кто зарегистрировался)
# */25 * * * * outreach.py — рассылка первого касания (ОСТАНОВЛЕНА 01.09.2026)
```
Порядок не случайный: `prepare.py` работает по свежей таблице, а `fillhash.py` —
по снимкам, которые `prepare.py` только что залил на сайт.

## «Первое касание» — авто-отправка авторам (`outreach.py`)

> **ОСТАНОВЛЕНА 01.09.2026 по решению Савелия** — «неудобно с ними работать».
> `python3 sendoff.py` снял флаг в `.env` **и убрал строку из расписания cron**.
> Код и вся история в колонке «Написали?» остались на месте; включить обратно —
> `python3 sendon.py` (он же вернёт строку в расписание). В `install_cron.py`
> рассылки больше нет намеренно: иначе перезапуск расписания включал бы её сам.
> Всё, что описано ниже, — про выключённую программу.

Отдельная программа рядом с парсером. Разведка при каждом новом объявлении с
ником автора кладёт его в очередь `outreach_queue.jsonl`; `outreach.py` берёт
из очереди и пишет автору **один раз**: «Здравствуйте! Ваше объявление ещё
актуально? <ссылка>». Дальше диалог ведёт Савелий сам, как человек.

Источник правды «кому уже писали» — колонка **«Написали?»** в таблице:
`Да` (написали), `Нет` (в очереди), **`Премиум`** (человек принимает письма
только от Telegram Premium — бот его НЕ трогает, пишет Савелий вручную; строка
жёлтая), **`Не доставлено`** (личка закрыта, ник исчез; строка серая). Бот берёт
в работу только `Нет`, а после отправки/отказа сам проставляет нужный статус
**во всех строках этого человека сразу**. Колонку «Присутствие» бот не читает
и не трогает — это отдельная воронка (см. раздел про мини-CRM выше).

Гарантии и щадящий режим:
- один автор = одно сообщение навсегда (вечный список `contacted.json`);
- отказ не «подвешивает» очередь: за запуск пробуем до `OUTREACH_MAX_ATTEMPTS`
  (5) авторов подряд, пока одно письмо не уйдёт; временные сбои — до
  `OUTREACH_FAIL_LIMIT` (3) попыток, потом «Не доставлено»;
- пишем только по объявлениям старше суток (`OUTREACH_MIN_AGE_HOURS`);
- с 2–3 личных аккаунтов по очереди; у каждого дневной лимит с прогревом
  (`OUTREACH_DAILY_START`→`OUTREACH_DAILY_MAX`, шаг `OUTREACH_WARMUP_STEP`);
- только «человеческие» часы по Бангкоку (`OUTREACH_HOURS`) + случайные паузы;
- **темп**: между двумя письмами одного аккаунта — минимум `OUTREACH_MIN_GAP_MIN`
  (25) минут плюс случайная добавка до `OUTREACH_GAP_JITTER_MIN` (10) минут.
  Правило живёт в файле состояния самого бота, поэтому его не сломает ни сбитое
  расписание cron, ни `OUTREACH_PER_RUN` больше единицы;
- если Telegram ограничил аккаунт (FloodWait/PeerFlood) — аккаунт уходит на
  паузу: первая блокировка 6 ч, вторая **подряд** сутки, третья и дальше трое
  суток (`OUTREACH_PEERFLOOD_STEPS`). «Подряд» = новая блокировка случилась в
  течение `OUTREACH_PEERFLOOD_RESET_HOURS` (24) часов после окончания прошлой
  паузы. Ушло письмо или сутки прошли спокойно — счёт заново с 6 часов;
- по умолчанию ВЫКЛЮЧЕНО (`OUTREACH_ENABLED=1` включает).


### Настройка
1. Для КАЖДОГО отправляющего аккаунта — вход одной командой (сессия сама ляжет
   в первый свободный слот `TG_SEND_SESSION_1..5` в `.env`):
   ```bash
   python3 loginsend.py   # номер (можно просто цифрами) → код из Telegram → пароль 2FA
   ```
   Запускать по разу на каждый аккаунт. Читающий аккаунт разведки `TG_SESSION` —
   отдельный, его не трогаем. Новый аккаунт стартует с прогрева
   (`OUTREACH_DAILY_START`), темп у каждого аккаунта считается отдельно.
2. Проверить план БЕЗ отправки (никому не пишет, только показывает, кому бы написал):
   ```bash
   OUTREACH_DRY=1 python3 outreach.py
   ```
3. Включить в `.env`: `OUTREACH_ENABLED=1` (или `python3 sendon.py`).
4. Разовый прогон прямо сейчас, мимо ограничения по часам: `python3 sendnow.py`.
